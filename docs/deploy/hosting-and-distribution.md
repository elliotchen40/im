# 部署与分发（无公网 IP / 上架合规）

> 回答两个高频问题：**「没有公网 IP 能用 Cloudflare 隧道吗？」** 和
> **「这 app 能过上架审核吗？」**
>
> 结论先给：**隧道可以，而且刚好合适；上架目前过不了**（原因与出路见 §3、§4）。
> 合规部分会随政策变化，请以华为官方最新审核意见为准。

---

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 没有公网 IP，能用 Cloudflare Tunnel 吗 | ✅ 可以，而且比公网 IP 更好（自带 HTTPS、隐藏源站、免端口映射） |
| 我们的长轮询会撞 Cloudflare 的超时限制吗 | ✅ **不会**：长轮询 35s < Cloudflare 免费版约 100s 静默超时 |
| 能通过华为应用市场审核吗 | ❌ 基本不能（App 备案 + 社交/IM 类资质 + 个人主体限制 + 内容风险，4 道门同时挡） |
| 那怎么装到自己手机上 | ✅ 不上架即可：DevEco 真机调试签名，直接装（见 §4） |

## 2. 部署形态 C：Cloudflare Tunnel（无公网 IP）

### 原理

```
app(手机) ──HTTPS──> Cloudflare 边缘 ──隧道出站连接──> cloudflared(你的机器) ──> 127.0.0.1:8081
```

`cloudflared` 在**你的机器上主动向外**连到 Cloudflare，所以：

- 不需要公网 IP、不需要路由器端口映射、不需要开 80/443
- 自动获得 HTTPS（这是我们把 `IM_APP_TOKEN` 放在 `Authorization` 头里所**必需**的）
- 源站 IP 不暴露

### 配置

**A. 快速临时隧道**（零配置，适合先试；URL 每次重启都变）

```bash
# 安装 cloudflared 后：
cloudflared tunnel --url http://127.0.0.1:8081
# 会输出形如 https://random-words-1234.trycloudflare.com 的地址
```

app 面板填那个 `https://...trycloudflare.com` 地址即可。

**B. 命名隧道**（推荐；固定域名 + 用自己的域名）

```bash
cloudflared tunnel login
cloudflared tunnel create im
cloudflared tunnel route dns im im.example.com
cloudflared tunnel run --url http://127.0.0.1:8081 im
```

服务端配合改成只监听本机（由 cloudflared 转发）：

```env
IM_BIND_HOST=127.0.0.1
```

app 面板填 `https://im.example.com`。

### 关键：为什么 35s 长轮询能安全穿过隧道

Cloudflare 免费版有一条**平台级硬限制**：源站在约 **100 秒**内没有吐任何数据，边缘就断连并返回
**524**（`Proxy Read Timeout`，免费/Pro/Business 固定不可调，只有 Enterprise 能改到 6000s）。

我们的 `/im/sync` 是**长轮询**：没消息时服务端挂起，所以"静默"时长正好是长轮询超时 ——

| 参数 | 值 | 与 Cloudflare 100s 的关系 |
|---|---|---|
| `IM_LONG_POLL_TIMEOUT_MS` | `35000`（35s） | ✅ 有 65s 余量 |
| app 侧 `readTimeout` | 40s | ✅ |
| 请求体上限 | 服务端 8 MiB / Cloudflare 免费版 100 MB | ✅ |

> ⚠️ **注意**：如果把 `IM_LONG_POLL_TIMEOUT_MS` 调到 **≥100 秒**，就会开始撞 524。
> 想更省电/更少请求而要拉长轮询时，请改用 WebSocket 或带心跳的 SSE，而不是无限拉长轮询。

### 别让 Cloudflare Access 挡住 app

如果用 Zero Trust 的 **Access** 保护这个域名，它默认要求**浏览器登录**，
而我们的 app 只发 `Authorization: Bearer <IM_APP_TOKEN>` —— 会被挡在门外。

两种做法：

1. **不开 Access**（推荐，个人自用）：直接靠 `IM_APP_TOKEN`。
   隧道本身已经把源站藏起来了，443 上暴露的只有一个需要 token 的 API。
2. **要开 Access 就配 Service Token**，让 app 额外带两个头
   `CF-Access-Client-Id` / `CF-Access-Client-Secret` ——
   这需要改 `app/.../services/ImClient.ets` 的 `headers()` 和 `AppConfig`（当前未实现）。

### 排查：隧道场景下的典型症状

| 症状 | 原因 |
|---|---|
| 每约 100s 断一次 | 有请求在源站静默超过 100s（长轮询被调太大，或某处是同步阻塞） |
| 约 60s 断一次 | 中间还夹了一层 Nginx（默认 `proxy_read_timeout 60s`） |
| 401 | token 不一致，或开了 Access 却没带 Service Token |
| 上传大图失败 | 撞 100MB 请求体上限（我们的图片是 base64 内联，膨胀约 1/3，要留意） |

## 3. 上架审核：现实结论是「过不了」

### 四道门，每道都能单独拦下

| # | 门槛 | 对我们的影响 |
|---|---|---|
| 1 | **App 备案**（工信部，2023-09 起"先备案后上架"） | 需通过接入商（华为云/阿里云等）办理，且**鸿蒙包名要单独备案**；未备案会在安装时提示"应用未核准（备案）"。个人主体也能备案，但需要域名 + 境内服务器等条件 |
| 2 | **即时通讯/社交类专项资质** | 华为《应用资质审核要求》对"聊天/社区/通讯/婚恋"类要求：**《安全评估报告》**（加公章）+ 在全国互联网安全服务管理平台的提交结果截图（状态需"通过"）+ **ICP 备案 或《增值电信业务经营许可证》** + 软著（三选一） |
| 3 | **主体限制** | 华为开发者问答的官方口径：**含 UGC 的社交类应用需要企业主体**，个人开发者不可上架；个体工商户在实践中也有分歧。我们这是"用户 ↔ AI"的聊天，审核上仍按聊天类看待 |
| 4 | **内容与功能合规** | 需实名认证、内容审核（先审后发）、**举报/投诉入口**、60 日以上日志留存、青少年模式；**生成式 AI 还要算法备案 + AI 生成内容标识材料** |

### 更致命的是内容定位

本项目承接的上游内核里，人格设定包含"依恋型的真人女友"这类 SOUL 人格，
且上游明确"**不做色情/性内容过滤**"。这类内容**必然过不了**应用市场的内容审核 ——
这不是改代码能绕过去的，是产品定位与审核规则直接冲突。

### 如果真要上架，需要做的事

1. 企业主体 + 软著 + 安全评估报告 + ICP 备案（或 ICP 许可证）
2. 剥离全部亲密/恋爱向人格，改成明确的工具类定位（如"个人 AI 记账/记事助手"）
3. 接入内容审核（先审后发）+ 举报入口 + 实名 + 青少年模式 + 日志留存 60 天
4. 生成式 AI 相关：算法备案 + 生成内容标识
5. 集成 Push Kit 而不是自建长连接（华为对鸿蒙 NEXT 应用的技术建议）

现实评估：**为一个自用 chatbot 走完这套流程的成本，远高于自用侧载。**

## 4. 不上架怎么装到自己手机（推荐路径）

HarmonyOS NEXT 允许用**调试签名**把未上架的 HAP 装到真机，完全绕开应用市场：

1. 注册华为开发者账号并完成**实名认证**（个人即可，免费）
2. DevEco Studio → `File → Project Structure → Signing Configs` → 勾选
   **Automatically generate signature**（用该账号自动生成调试证书与 Profile）
3. 手机开启「开发者模式 + USB 调试」，连上电脑
4. DevEco 里点 Run → HAP 直接装到手机上
5. 应用有效期与调试 Profile 绑定（通常需要定期重签），个人自用足够

**分享给朋友**的几种方式：

| 方式 | 可行性 |
|---|---|
| 让朋友也装 DevEco + 用你的调试 Profile 签名 | 可以，但 Profile 的**设备列表**有限额，且朋友要会折腾 |
| AppGallery Connect 的**内测/开放式测试** | 环节比正式上架少，但仍要账号与备案信息，且有人数限制 |
| 直接发 `.hap` 文件 | ❌ 不可行：未签名/签名不匹配的设备装不上（系统会拦） |

**结论**：自用 → 侧载最省事；给少数人用 → 内测；面向公众 → 必须走 §3 的全套合规。

### 4.1 AGC 内测到底能用多久（≤90 天，且到期会真失效）

先分清 AGC 的几种测试 —— 上限与时效完全不同：

| 测试类型 | 适用 | 人数/设备上限 | 测试时间最长 | 需企业主体 |
|---|---|---|---|---|
| **邀请测试** | HarmonyOS **API ≥ 10**（我们属于这种） | 内部群组 100 / 外部 10000 | **90 天** | 否 |
| 公开测试 | HarmonyOS API ≥ 10 | 下载安装上限 1000 万次 | **30 天** | 否 |
| 开放式测试 | **仅 Android 或 HarmonyOS API ≤ 9** | 免审 100 / 非免审 5000 | 90 天 | 否 |
| 指定设备发布（原「内部测试」） | 按设备 UDID 授权、不上架市场 | **100 台设备** | 版本有效期 **90 天** | **是（企业）** |

> ⚠️ 对我们最要紧的两点：
> 1. 我们是 HarmonyOS NEXT（API ≥ 10），**不能用「开放式测试」**，只能走**邀请测试**或公开测试。
> 2. 官方口径：测试时间到期后，已参与用户仍可继续用，**直至安装时间超过 90 天，之后应用无法启动**。
>    也就是说内测**不是「装上就永久能用」**，而是一个 ≤90 天的窗口。

**到期了怎么办**：

- 未到期：在 `版本列表` 里修改测试时间（**开始与结束的跨度不得超过 90 天**；
  「正在测试」状态只能改结束时间）。
- 已到期/已失效：**原版本不能恢复**，必须**递增 versionCode** 新建测试版本、重新提交审核
  （人工审核约 1–3 个工作日）。
- 于是长期自用走内测的代价是：**每 90 天折腾一次**（改版本号 → 重新打包 → 重新提交 → 用户重新安装）。

**对个人自用来说这不划算** —— 侧载的周期更长：

| 方式 | 周期 | 需企业主体 | 到期后 |
|---|---|---|---|
| **DevEco 调试签名侧载** | 调试证书 **1 年**（未实名开发者仅 **14 天**） | 否 | 重新签名安装 |
| AGC 邀请测试 | 90 天 | 否 | 已装应用在安装满 90 天后失效，需重建版本 |
| 指定设备发布（UDID） | 90 天 | **是** | 递增版本号重新部署 |
| 正式上架 | 长期 | 是 + §3 全套资质 | 应用内更新即可 |

所以：**个人自用 → 侧载；要给几十上百人用 → 邀请测试；面向公众 → 只有正式上架一条路。**

备案补充：内测/邀请测试阶段通常**不要求** ICP 备案（以 AGC 提交页的实际提示为准），
但**公开测试与正式上架页面会要求配置备案信息**；纯单机不联网的应用可豁免。

## 5. 推荐组合（个人自用）

```
服务器（家里的机器/云主机，无公网 IP 也行）
  └─ im server 监听 127.0.0.1:8081
  └─ cloudflared 命名隧道 → https://im.example.com（自动 TLS）

鸿蒙 app
  └─ DevEco 调试签名侧载到自己的手机
  └─ 配置面板填 https://im.example.com + IM_APP_TOKEN
```

这套组合：不需要公网 IP、不需要端口映射、全程 HTTPS、不经过任何应用市场审核。
